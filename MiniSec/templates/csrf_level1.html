实验说明 Description

这是一个「修改资料」功能。它靠 Cookie（会话）来认人 —— 这本身没问题，问题在于它没有校验这个请求是从哪来的：
POST /labs/csrf/level1/profile

表单里其实带了 CSRF 令牌，但后端从来没有看过它 —— 「加了但没校验」等于没加。
The form does carry a CSRF token, but the backend never validates it. A token that is not checked is the same as no token.

通关判定：数据库里 victim 的邮箱被改成了攻击者指定的地址 {{ attacker_email }} 即视为通关。 判定看的是数据库里真实的值，不是你提交了什么。
Completion rule: the victim's email must become {{ attacker_email }}. The check looks at the database, not at what you submitted.

本项目的对照设计：平台自身的接口（登录、恢复出厂…） 由 security.py 全站校验 CSRF 令牌； 只有这一关的靶子接口被故意放进豁免名单，用来演示「不校验会怎样」。 豁免名单在 security.py 里，并注明"只给靶子用"。
For contrast: this project's own endpoints are protected globally by security.py. Only this lab's target endpoint is deliberately exempted, so you can see what happens without that protection.

The identity comes from the session cookie — as in any real system. The key fact: the browser attaches cookies automatically, no matter who initiated the request.

代码里两个"没做"凑成了这个漏洞： 没校验请求来源、没校验那个已经放进表单的令牌。 身份判断（Cookie）本身没问题 —— 有问题的是只做了身份判断。
Two omissions create this bug: the origin of the request is never checked, and neither is the token that is already sitting in the form. Identifying the user by cookie is fine; doing only that is not.
